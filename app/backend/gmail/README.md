# BackendGmail notes

## Folder mapping (Task 3, by Gmail label id, not name)

- INBOX -> displayname "Inbox", type INBOX (2), parentid "0"
- SENT -> "Sent", SENTMAIL (5), "0"
- DRAFT -> "Drafts", DRAFTS (3), "0"
- TRASH -> "Trash", WASTEBASKET (4), "0"
- SPAM -> "Junk", USER_MAIL (12), "0" (per BackendIMAP pattern: Spam is USER_MAIL named Junk)
- ALLMAIL (synthetic, not a Gmail label) -> "All Mail", USER_MAIL (12), "0"; message-list handling (no label filter) comes in Task 4
- User labels (type user, not skipped) -> displayname = label name, USER_MAIL (12), "0", flat (no hierarchy in v1), sorted by name
- Order in GetFolderList: system folders in fixed order [INBOX, SENT, DRAFT, TRASH, SPAM] (only those present), then ALLMAIL, then user labels sorted by name. GetFolderList returns array of ['id'] (like BackendIMAP); GetHierarchy composes SyncFolder objects via GetFolder.

## Skips (v1, not folders)

- Exact (by label id): STARRED, IMPORTANT, UNREAD, CHAT. Plan lists STARRED/CATEGORY_*/IMPORTANT; UNREAD + CHAT are added by the same principle (attribute/status labels, not folders; UNREAD as a folder would duplicate all unread mail, CHAT would show Hangouts chats as mail).
- Prefix (by label id): CATEGORY_*
- [Imap]/Trash is NOT skipped in v1: it is the only user label in this account, and plan's test requires a known user label present. If it becomes clutter later, add a skip rule with user approval.

## Logon (Task 3 + Task 10 design)

- Logon does: (1) create GmailApiClient from config token/client files, (2) labels.list probe (fails -> Logon false), (3) if GMAIL_LOGON_IMAP_PROBE (default true), IMAP probe: imap_open to imap.gmail.com with device username/password, OP_HALFOPEN, close immediately (fails -> Logon false). Password is used only for the probe, then discarded (never stored). Username/domain are stored (for GetCurrentUsername); password is not.
- GMAIL_LOGON_IMAP_PROBE can be pre-defined false before including config.php (tests do this: no real IMAP app password in test env). Live probe success is verified in Task 10 (real device).
- Logoff clears the API client + folder cache. No backend storage is used yet in Task 3; Tasks 5/7 will add storage handling if needed.

## Sync model (important, Task 3 discovery)

- Z-Push has NO GetChanges interface method (grep over the whole app returns empty). BackendGmail extends BackendDiff per plan, so framework Sync uses GetMessageList + StatMessage (Diff), NOT GetChanges.
- Task 5's GetChanges will be an internal history helper (tested directly per plan's tests, used for high-water tracking + debugging), NOT wired into framework Sync. High-water for ChangesSink (Task 7) is updated on every successful GetMessageList (via getProfile), not only via GetChanges, so Ping wakeup works in Diff model.
- MVP Sync therefore does full list scans (like the IMAP backend). History-based Sync optimization (custom Exporter) is deferred to post-MVP.

## State keys (planned, Tasks 5/7)

- Per-folder lastHistoryId (via Z-Push state machine, keyed by folderid).
- Global historyId high-water (for ChangesSink comparison + debugging).
- Wake flag file: GMAIL_WAKE_FLAG_FILE (Task 8, Phase 2).

## Task 4 notes (message list + fetch)

- GetMessageList(folderid, cutoffdate) returns messages with id, mod, flags, answered, forwarded, star (for Diff getDiffTo). mod = sha1(implode(',', sorted labelIds) + '|' + internalDate). flags = 1 if read (UNREAD absent) else 0. star = 1 if STARRED present else 0. answered = forwarded = 0 always (Gmail API has no such flags). GetMessageList and StatMessage share computeStat() so mods agree.
- GetMessageList fetches metadata per message (O(N)) because listMessages returns only id + threadId (no labelIds/internalDate). Bounded by cutoffdate (recent messages only, not all-time). 404 on metadata fetch = skip that id (race: message deleted between list and fetch).
- Cutoffdate: API q "after:YYYY/MM/DD" (from cutoffdate - 1 day buffer, UTC) + client-side exact filter internalDate >= cutoffdate*1000 (millis). cutoffdate == 0 means no date filter (list all, paginated).
- All Mail: labelId null + q "-in:trash -in:spam" (+ cutoff q if any) + client-side defensive filter (skip labelIds containing TRASH or SPAM). Gmail's All Mail inherently excludes Trash/Spam; q + filter ensure it even if API quirks return them. Non-All Mail folders do NOT filter TRASH/SPAM (TRASH folder must list TRASH messages).
- GetMessage(folderid, id, contentparameters) returns SyncMail object (not raw string) with asbody type MIME, data = raw MIME (StringStreamWrapper::Open), estimatedDataSize = strlen, truncated = 0, nativebodytype = PLAIN. It ignores $contentparameters truncation/body preference (always full MIME; IMAP never truncates MIME either, and iPhone wants MIME). Headers are parsed from raw MIME (unfold + first-wins + RFC2047 decode via iconv_mime_decode if available). To/cc/reply_to via Mail_RFC822 (like IMAP, with raw fallback + group handling). datereceived via cleanupDate (strtotime after stripping parenthesized comments). Protocol-gated fields (contentclass, flag, lastverbexecuted) follow IMAP gating (12.0/14.0).
- GetAttachmentData stays a stub throwing StatusException INVALIDATT (separate FetchAttachment deferred; attachments are delivered inline in MIME body for Sync, and GetMessage leaves asattachments empty so clients will not request separate fetches for normal Sync).
- GmailApiClient::listMessages gains optional $q param (3rd, default null, backward compatible) for All Mail exclusion + cutoff after: filter.

## Task 5 notes (history incremental sync + high-water)

- GetChanges(folderid, &state, cutoffdate = 0) is an internal history helper (NOT framework Sync; framework uses Diff via GetMessageList + StatMessage, since Z-Push has no GetChanges interface). state is array with 'lastHistoryId' (by reference, updated in place). Returns changes array (each: id, type added/changed/deleted, mod + flags for added/changed).
- Baseline (no lastHistoryId): SKIPS full list (deviation from plan's "先全量列一次", justified by Diff architecture + performance): sets lastHistoryId = current profile historyId, returns empty. Initial load must use GetMessageList (Task 4), not GetChanges.
- History mapping (probed 2026-10-29, real API): history.list returns records in ascending historyId order, 100 per page, response historyId = current. Detailed records carry message.labelIds = full current labelIds after change + labelIds = added/removed labels only. Trash = 2 records (labelsAdded TRASH, then labelsRemoved INBOX, consecutive historyIds). Messages-only records (no Added/Removed details, rare) are handled via metadata fetch (404 -> deleted, in folder -> changed, else ignore). messagesDeleted ignored in v1 (Diff covers permanent deletes; tests never permanently delete).
- Mapping rules: messagesAdded + in folder -> added. labelsAdded + folder label newly added (non-ALLMAIL) -> added (not changed; fixed after first Green run where TRASH add was misreported as changed). labelsAdded + already in folder (other label added) -> changed. labelsRemoved + still in folder -> changed. labelsRemoved + folder label removed (non-ALLMAIL) -> deleted. ALLMAIL: labelsAdded TRASH/SPAM -> deleted (leaving All Mail); labelsRemoved alone never means leaving All Mail (ignored for ALLMAIL to avoid duplicate deleted, since labelsAdded TRASH already reports it). No coalescing within a single call (history-ordered, caller applying sequentially ends with final state).
- Fallback on history.list 404 (expired/future/old historyId, e.g. '1', '0', current+1000000 all 404 with NOT_FOUND) OR 400 with 'startHistoryId' in message (out-of-int64-range values like 20-digit numbers return 400 INVALID_ARGUMENT, not 404). Fallback: discard lastHistoryId, full list via GetMessageList as added changes, reset lastHistoryId = current profile historyId. Idempotency = re-run changes' ids do NOT intersect fallback ids (tolerates new mail arriving between calls).
- High-water: file-based (config GMAIL_HIGHWATER_FILE = '/var/lib/z-push/.gmail-highwater.json', atomic temp + rename, 0600, max-only update, failures logged but never fail Sync). Updated on every successful GetChanges + GetMessageList (via getProfile). In-memory only would not persist across EAS requests (Ping needs cross-request high-water); file in /var/lib/z-push/ persists via state volume in production, and within single direct-test container run for tests.
- ChangesSinkInitialize NOT implemented in Task 5 (leaves base false); Task 7 implements ChangesSink + ChangesSinkInitialize together (to avoid half-implemented Ping claiming sink available but returning no wakeups).
- Multi-label test uses API modifyMessage (remove UNREAD) to simulate read, NOT BackendGmail SetReadFlag (Task 6); history record is identical. LabelX = [Imap]/Trash (only user label, looked up by name at runtime).

## Task 6 notes (core write ops + new sends; SmartReply merging still open)

- SetReadFlag(folderid, id, flags, contentParameters): flags 1 = read (remove UNREAD), 0 = unread (add UNREAD), loose == like IMAP. folderid ignored for API call (read is global in Gmail, not per-folder); 404 (message gone) returns true (idempotent success), other API errors propagate. Note: mod includes UNREAD (Task 4 definition), so marking read changes BOTH flags and mod; Diff will report flags change + mod change (full item re-send + flags update, redundant but correct, per Diff docs warning; acceptable for MVP, read ops are infrequent).
- DeleteMessage(folderid, id, contentParameters): NEVER permanently deletes (only trash / remove source label). Logic: fetch metadata first (404 -> return true, already gone); if folderid == TRASH and message already has TRASH -> return true (no-op, Trash delete cannot remove from Trash view without permanent delete, which v1 forbids; message stays in Trash until 30-day auto-expiry); else if folderid == INBOX or ALLMAIL -> trashMessage (add TRASH, remove INBOX, disappears from source view via TRASH exclusion for ALLMAIL, via INBOX removal for INBOX); else if folderid is a real label (in loadLabels) -> modify add TRASH + remove source label (disappears from source + appears in Trash; trashMessage alone would keep source label for non-INBOX sources, violating delete semantics, so modify is required); else (unknown/stale folder) -> trashMessage fallback. No cutoff check (unlike IMAP, which throws OBJECTNOTFOUND outside sync range; Gmail API allows any message, device only requests synced ones, and stale-folder deletes should still trash, not fail).
- MoveMessage(folderid, id, newfolderid, contentParameters): returns same id (string, Gmail id stable across labels, unlike IMAP UID which changes; Importer expects new id string, so returning same id is correct). Same-folder -> SYNC_MOVEITEMSSTATUS_SAMESOURCEANDDEST; unknown source -> INVALIDSOURCEID; unknown dest -> INVALIDDESTID; message not found (404) -> INVALIDSOURCEID; API failure -> CANNOTMOVE. Move via single modify: dest TRASH -> add TRASH + remove source (if real, not ALLMAIL); dest ALLMAIL (archive) -> remove source only (no add, All Mail automatic); dest real label -> add dest + remove source (if real, not ALLMAIL); source ALLMAIL -> add only (labeling, stays in All Mail, since All Mail includes labeled messages; true move-out of All Mail is impossible except via trash). No cutoff check (same reasoning as Delete). Idempotent: moving a message already in dest / already not in source still succeeds (add/remove are no-ops for already-present/absent labels).
- SendMail(sm) core (full MIME path): If sm->mime empty -> SYNC_COMMONSTATUS_MAILSUBMISSIONFAILED. Else send sm->mime directly via GmailApiClient sendMessage (which base64url-encodes internally). From/To/Subject/body/attachments are as composed by device (iPhone Mail already RFC2047-encodes non-ASCII subjects, builds multipart correctly); server does NOT re-encode, does NOT override From (API validates From vs authenticated user / send-as), does NOT save to Sent separately (API auto-saves to Sent). saveinsent ignored (API always saves; extra Sent copy when client said don't save is harmless, missing copy would be worse). API failure -> SYNC_COMMONSTATUS_MAILSUBMISSIONFAILED (not raw GmailApiException, so EAS client gets proper send-failure code).
- SendMail SmartReply/Forward gap (OPEN, next step within Task 6, before Task 7): If sm->source present + replacemime false/absent + replyflag/forwardflag set, current code logs a warning and sends sm->mime as-is (degraded: reply without threading headers (In-Reply-To/References) and without quoted original, forward without original .eml attachment; message still delivered, but not threaded / forward lacks original). Production logs show 0 SendMail calls in 12 days (user has not sent via iPhone EAS yet), so iPhone SmartReply usage is unproven from logs, but iOS EAS is known to use SmartReply for replies; IMAP backend handles it via source fetch + addTextParts + .eml attach, so Gmail backend must match it before Task 10 switch to avoid reply regression. Do NOT mark Task 6 complete until SmartReply/Forward merging + tests (testSmartReply, testSmartForward) pass.
- Test lesson (SendMimeFidelity, fixed 2026-10-29): Test MIME Subject with raw UTF-8 Chinese (not RFC2047-encoded) causes Gmail to store mojibake subject (double-encoded Latin-1), breaking subject === comparison. Real devices always RFC2047-encode non-ASCII subjects; test builder now uses mb_encode_mimeheader (B encoding, UTF-8). Verified: mb-encoded folded subject (2 encoded-words) decodes via iconv_mime_decode (mode 1) to exact original (whitespace between adjacent encoded-words correctly ignored per RFC 2047), so long folded subjects round-trip exactly. Backend GetMessage unfolding (CRLF+WSP -> single space) + iconv decode is correct for folded subjects.

### Task 6 SmartReply/Forward (completed 2026-10-29, after Task 7 code, before Task 10)

- SendMail Smart path (replaces the Task 6 core WARN + passthrough): triggered only when source itemid present AND replacemime not true AND replyflag or forwardflag truthy (reply takes precedence if both, matching IMAP if/else-if). hasSource requires itemid only, NOT folderid (deviation from IMAP, which throws ITEMNOTFOUND on unmapped source folder; Gmail ids are global, folder mapping is unnecessary, and sendmail.php may leave folderid empty on stale mapping — requiring it would silently drop merging for stale folders).
- Reply merging (IMAP addTextParts structure, copied): new plain/html + quoted source (plain: ">\r\n" separator + "> " per line; html: "<blockquote>" + source html, or "<p>" + plain source if source has no html; plain fallback uses Utils::ConvertHtmlToText(htmlSource) if source has no plain). New attachments via addExtraSubParts (copied from mime_encode.php, as private methods to keep Gmail backend self-contained, no cross-backend require). Reply does NOT include source attachments (IMAP comment, preserved).
- Forward merging (IMAP non-inline default, IMAP_INLINE_FORWARD not defined in Gmail backend): new plain/html/calendar via addTextPartsMessage + new attachments via addExtraSubParts + source raw as message/rfc822 base64 attachment, disposition attachment, dfilename forwarded_message.eml. Forward does NOT inline-quote source and does NOT set threading headers (new thread, matching IMAP).
- Threading (improvement over IMAP, which relies on Subject only): reply sets In-Reply-To = source Message-ID and References = (source References + " " + source Message-ID) or just source Message-ID, from authoritative source raw headers (source fetched via API getMessage raw, not from device, since EAS SyncMail carries no Message-ID). Source without Message-ID -> threading skipped with WARN, quoted body still sent (degraded, not failed).
- Final headers use RAW new-mime headers (unfolded, NOT decoded, original casing, first-occurrence wins, case-insensitive dedup), skipping content-type/content-transfer-encoding/mime-version, plus encoded multipart/mixed Content-Type from Mail_mimePart, plus MIME-Version 1.0. Raw copying preserves device RFC2047 encoding exactly (no decode/re-encode round-trip, unlike IMAP which decodes then re-encodes Subject/To/Cc/Bcc). Only fix: Subject containing raw UTF-8 bytes (invalid, ASCII-only encoded-words would not trigger) is mb_encode_mimeheader-encoded, matching IMAP's Subject fix for the Task 6 core mojibake case. From fallback to Logon username if new mime lacks From (should not happen for iPhone, but safe).
- Empty-reply improvement over IMAP: addTextParts adds a part if EITHER new body OR source exists (IMAP skips both parts when new body is empty, losing quoted context entirely). Empty reply to non-empty source now carries quoted source only (plain starts with separator + quoted lines, html starts with blockquote), instead of empty body. Normal non-empty replies unchanged. Forward with empty new body needs no fix (eml attachment preserves source, empty body is intended).
- Bypass cases (all passthrough, never fail send): S/MIME new mime (top-level Content-Type multipart/signed, application/pkcs7, application/x-pkcs7, multipart/encrypted) or calendar in new mime (text/calendar or BEGIN:VCALENDAR anywhere, matching IMAP getSendArray bypass for S/MIME/calendar, to preserve signatures/calendar objects); source fetch failure (404, empty raw, decode failure) -> passthrough with WARN; merging exception (any Throwable in buildSmartMime, including missing mbstring/Utils) -> passthrough with WARN. Passthrough send failure still throws MAILSUBMISSIONFAILED (send itself failed, not merging). Answered/forwarded marking NOT implemented (Gmail API has no Answered/Forwarded flags; Task 4 hardcodes answered=forwarded=0; reply/forward will not show replied/forwarded icons on originals in v1, known limitation, not a send failure).
- Tests: /opt/zpush-gmail/tests/gmail_backend_smart_test.php (4 tests, directory-mount run, Green first try 25s): testSmartReply (In-Reply-To/References == orig Message-ID, plain quoted with "> ", html blockquote, new attachment preserved), testSmartForward (no In-Reply-To/References, forwarded_message.eml present, eml body contains orig plain + orig attachment, getBodyRecursive plain contains new only, not orig inline, new attachment preserved), testSmartReplySourceMissingFallback (fake id -> return true, new body delivered as-is, no throw), testSmartReplaceMimeBypass (replacemime=true + valid source -> no quoting, no threading, new body only). Red was 2/4 (reply/forward FAIL on merging assertions, fallback/replacemime PASS as passthrough already correct).

## Task 7 notes (ChangesSink + history polling wake)

- HasChangesSink() returns true (base default false would make framework fall back to CountChanges polling via exporter, not Sink). ChangesSinkInitialize(folderid) validates via resolveFolderLabel (ALLMAIL valid virtual, unknown -> return false, not throw, so framework throws proper ERROR_WRONG_HIERARCHY); valid folders are added to in-memory $watchedFolders (dedup, per-Ping-request only, new Backend instance per EAS request, no file persistence needed, unlike high-water file).
- ChangesSink($timeout) returns array of backendFolderIds (NOT bool): framework SyncCollections::CheckForChanges foreaches the return, maps each via GetFolderIdForBackendId, then CountChange (Diff via GetMessageList+StatMessage) to validate relevance; returning bool true would foreach-warn and never wake (plan's "返回 true" is read as non-empty watched array). Empty watched -> return [] immediately (framework never calls Sink without Initialize).
- Polling: check immediately at t=0, then sleep min(GMAIL_POLL_INTERVAL=10, remaining) until timeout, then return []. Short timeouts respected (e.g., Sink(5) sleeps 5, not full 10, otherwise test elapsed would overshoot). On historyId > high-water (or high-water null on first Ping), updateHighWater(current) BEFORE returning watched (prevents repeated false wakes for same change when CountChange validates false for non-watched folders; updateHighWater is max-only, safe). Null high-water -> return watched immediately (wake, device Syncs initial messages) rather than silently baselining and missing a message that arrived during first Ping (which would delay it up to Ping lifetime).
- Never throws: getProfile failures are caught, logged WARN with HTTP status only (no body/secrets), treated as no-change for that check, polling continues until timeout, then []. This applies Task 9兜底 principle early to Task 7 (transient 429/network must not break Ping; persistent 401 will still surface as never waking, not as Ping error loop).
- Non-consuming proof: Sink only calls getProfile + high-water file, never GetChanges (which would need per-folder $state) and never touches device Sync state; direct test proves it by establishing GetChanges baseline, sending, Sink-waking, then GetChanges from same baseline still returns test message as added + GetMessageList still contains it.
- Test flakiness lesson (NoChangeTimeout, fixed 2026-10-29): asserting "no change" on a live mailbox fails if real mail arrived since last high-water update (stale high-water from previous runs, 8 minutes earlier, contained real arrivals, Sink correctly woke). Test-instance compose fixed the same way: removed secrets single-file mounts, secrets now live inside state volume (docker cp + chown www-data + chmod 0600, verified www-data can create+rename inside volume, smoke HTTP 401, production still up). Without this fix, test-instance API backend would break 1h after token issue (refresh 401) during Task 10 verification. Direct-test high-water file now lives in secrets dir due to directory mount (just a historyId number, not a secret, harmless).
